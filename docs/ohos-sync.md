# Syncing `ohos-main` with upstream

`ohos-main` is `main` (a mirror of `upstream/main`) plus an ordered patch
stack. It is rebased regularly and force-pushed. This is the runbook; it is
written so an agent session can run a sync end to end with only
"run the sync runbook in docs/ohos-sync.md" as instruction.

Rules the runbook implements come from `CONTRIBUTING.md`. Where the two
disagree, `CONTRIBUTING.md` wins and this file must be fixed.

## Terms

- `base/<date>`: the upstream commit the stack sits on after the sync.
- `pre-sync/<date>`: the `ohos-main` tip before the sync (recovery point and
  left side of the range-diff review). Prunable after a few good syncs.
- `sync/<date>`: the `ohos-main` tip after the sync. Permanent.
- Stack manifest: `docs/ohos-sync/STACK.md`, the ordered list of patches on
  the stack (tier, test coverage, upstream watch paths), plus a per-sync log
  of conflicts, drift verdicts and drops. Checked against
  `git log base/<date>..ohos-main` by `docs/ohos-sync/check_stack.py`.
- Patch set: `docs/ohos-sync/patches/`, generated by `gen_patches.py`,
  verified by `check_stack.py` (`git am` onto the base must reproduce the
  tree). Its diff between syncs shows exactly which patches changed and
  how — the reviewable form of the range-diff.

## What a sync review consists of

A rebase can go wrong in three ways, and each needs its own evidence:

1. We changed a patch (conflict resolution, shrink, drop): visible in the
   `patches/` diff and the range-diff. Reviewed hunk by hunk.
2. Upstream changed something a patch relies on without a textual
   conflict (semantic drift, duplicated functionality, stale rationale):
   invisible in any diff. Surfaced by the drift report (`drift.py`) — every
   hit gets a written verdict in the sync log, and a hit against a patch
   with `manual` coverage means that patch's `Validation:` steps are run,
   not merely classified.
3. Everything else: the test gate (below). Coverage is uneven — `STACK.md`
   says which patches rest on 2 alone.

## Decisions (fixed, do not re-ask)

1. Base = the tip of `upstream/main` at the time of the sync, unless the
   sync request names a commit.
2. `Cargo.lock` is never merged by hand. Resolve to upstream's version, then
   regenerate the fork's additions with `cargo update -p <crate>` /
   `cargo metadata --locked` until it is consistent.
3. When upstream has landed something equivalent to a patch, the patch is
   NOT silently dropped. Verify equivalence by running the patch's
   `Validation:` steps against plain upstream. Then keep an empty commit
   whose message states it was dropped in favor of upstream (`Superseded-by:
   <upstream commit>`), who verified equivalence and how. Upstream doing
   strictly more is fine; any regression stops the sync and is escalated to
   a human. Empty placeholders are removed in the next sync's fold step
   (step 2), and the drop is recorded in the manifest log.
4. Every rebased commit gets `Signed-off-by` of the person running the sync
   (`git rebase --signoff`).
5. If an agent resolved a conflict, the commit gets an `AI-assisted:` trailer
   (or an extra line on the existing one) that says what was changed, or
   "mechanical conflict resolution, no semantic change". Never-conflicting
   commits are not touched.
6. Validation is a hard gate: all steps below must pass or be explicitly
   answered by a human before `ohos-main` is force-pushed.
7. Never push from an agent session. The human pushes the branch and tags.

## Procedure

### 0. Prepare

```sh
git fetch upstream main
git tag pre-sync/<date> ohos-main
git tag base/<date> upstream/main
git worktree add -b ohos-sync-<date> <worktree-dir> ohos-main
```

Use a private cargo target dir for the worktree (see the workspace
`AGENTS.md` if working in the servo-workspace container).

Predict the conflicts before starting, and list the upstream commits that
touch files the stack touches — this is the briefing for conflict
resolution:

```sh
git merge-tree --write-tree upstream/main ohos-main | grep ^CONFLICT
git diff --name-only base/<prev>..pre-sync/<date> | grep -v '^ports/arkweb/' \
  | xargs git log --oneline base/<prev>..base/<date> --
```

Run the drift report and keep its output; the verdict column is filled in
during step 3 and goes into the sync log:

```sh
uv run docs/ohos-sync/drift.py base/<prev> base/<date> ohos-main > drift.md
```

It lists, per patch, upstream commits touching the patch's own files and
its `watch:` paths from `STACK.md`, plus a keyword scan of upstream
subjects. This is how upstream equivalents (decision 3) and stale
rationale are found when nothing conflicts. If a patch gained a new
dependency surface, extend its `watch:` list in the same sync.

### 1. Rebase

```sh
git rebase --signoff --rerere-autoupdate --onto base/<date> base/<prev> ohos-sync-<date>
```

`rerere` is enabled in the repo; recurring resolutions replay automatically.

For each stop:

- Read the commit's message: intent and `Validation:` trailer.
- Read the upstream commits that touched the conflicting hunks
  (`git log -p base/<prev>..base/<date> -- <file>`).
- Resolve, keeping the patch minimal against upstream-owned files (prefer
  taking upstream's version and re-adding the fork's hook).
- `Cargo.lock`: `git checkout --theirs`-equivalent is wrong here since in a
  rebase "ours" is upstream; take the upstream side, then
  `cargo metadata --locked` and fix by `cargo update -p` on the fork's own
  dependencies only.
- Compile-check the crate(s) affected before continuing:
  `./mach check --ohos -p <crate>` (arkweb and other OHOS-only crates are
  not checkable on the host target).
- Write the final message (original text, the `AI-assisted:` line from
  decision 5) to a file, stage the resolution and commit it with

  ```sh
  git commit -s -F <file> --author="$(git log -1 --format='%an <%ae>' REBASE_HEAD)" \
    --date="$(git log -1 --format=%ad REBASE_HEAD)"
  ```

  then `git rebase --continue`. Without `--author`/`--date` the sync runner
  becomes the author of someone else's patch. Do not rely on amending after
  `--continue`: the rebase runs on through every cleanly-applying pick, so
  the commit is out of reach by then.

If a patch applies empty, or applies but a `git log --grep` / file search
shows upstream landed an equivalent: apply decision 3.

### 2. Fold (when the stack has something to fold)

A sync has two history-rewriting steps: the rebase (step 1) moves the stack,
folding reshapes it. Do all folding here — after the rebase, before
validation — so the stack is validated exactly once, in its final shape.

Fold, via `git rebase -i base/<date>`:

- fixup/follow-up commits into the commit they fix, tests into the commit
  they test (a standalone fix commit survives only when its message carries
  root-cause information worth keeping);
- empty placeholder commits from a *previous* sync's supersede (decision 3)
  are dropped now, one sync after they were created;
- patches that upstreaming has whittled down can be merged with their
  remaining sibling if that leaves one coherent patch.

Rules:

- Tree identity: folding must not change content. `git diff <pre-fold-tip>
  HEAD` must be empty; record the pre-fold tip in the sync report.
- Ordering: a commit may only move earlier if nothing it needs (files,
  features, README content its tests read) lands later — check with a quick
  `git rebase -i` dry run; a failed pick means the move is illegal.
- Messages: the surviving commit keeps its primary author; merge the
  `Validation:` trailers (union of steps, deduplicated) and keep every
  `AI-assisted:` line; note the fold in an added `AI-assisted:` line if an
  agent performed it.
- Bookkeeping: update `STACK.md` (entries removed/renamed) and list every
  fold in the sync-log entry — what was folded into what, and why. The
  manifest history is the record of when patches disappeared.

If there is nothing to fold, say so in the sync report ("fold: nothing to
do") rather than skipping silently.

### 3. Validate

Everything here runs in the sync worktree on the rebased stack.

Mandatory:

1. `./mach fmt --check` (or `./mach fmt` and confirm no diff), `./mach test-tidy`.
2. `./mach check --ohos` for the whole workspace; then per-crate host tests
   for stack crates that have them: `./mach test-unit -p servo-storage`,
   `./mach test-unit -p arkweb` (host-tested module).
3. Full OHOS release build:
   `./mach build --ohos --release --no-package -p arkweb` and the servoshell
   HAP build as used by the stack's Validation trailers.
4. Deploy and run the on-device arkweb suite on an OpenHarmony device
   (`ports/arkweb/README.md`, "On-device tests"); with several devices
   attached set `HDC_TARGET`. If every test fails with
   `HdcDisconnectedError`, the device dropped off the hdc server:
   `hdc kill; hdc start -r`, then rerun.
5. Walk every `Validation:` trailer of the stack
   (`git log --format='%h %(trailers:key=Validation,valueonly,unfold)' base/<date>..HEAD`)
   and classify each: ran and passed / ran and failed / needs a human
   (hardware or judgment). Commits that conflicted or were touched by
   upstream churn in the same files must have their steps run, not just
   classified.
6. Drift verdicts: one line per hit in `drift.md` — no effect / mirrored
   in commit X / rationale updated / superseded (decision 3) / needs a
   human. Hits against `manual`-coverage patches escalate to running that
   patch's `Validation:` steps.
7. Stack integrity:
   `git range-diff base/<prev>..pre-sync/<date> base/<date>..HEAD`
   read in full; every commit has a non-empty `Validation:` trailer;
   regenerate the patch set and check everything:

   ```sh
   uv run docs/ohos-sync/gen_patches.py base/<date>
   git add docs/ohos-sync/patches   # amend into the docs/manifest commit
   uv run docs/ohos-sync/check_stack.py base/<date>
   ```

Any failure is a regression until proven a pre-existing upstream issue
(check the same test on plain `base/<date>`). Regressions are fixed on the
stack (in the commit that owns the code) before hand-off.

### 4. Hand off

Update `docs/ohos-sync/STACK.md` (manifest + sync log entry with the drift
verdicts) and the patch set in the first commit of the stack and write the
sync report:

- upstream range (`base/<prev>..base/<date>`, commit count),
- conflicts and how each was resolved,
- drift hits and verdicts, and which manual validations they triggered,
- patches superseded/dropped (decision 3) with the equivalence evidence,
- validation results, verbatim for anything that failed or was skipped,
- open items that need a human decision.

The human reviews the sync with:

```sh
git diff pre-sync/<date> ohos-sync-<date> -- docs/ohos-sync
```

Reading it: most rebased patches should show exactly one added
`Signed-off-by` line (message-only). A few more lines of `index`/hunk-header
context churn appear in patches touching files upstream also modified
(`Cargo.lock` above all) — noise, but it marks where context drifted.
Everything else is a real change and is read hunk by hunk against the
conflict/drift notes in the sync log; STACK.md's diff carries the sync-log
entry itself. On the forge the same view is the `pre-sync/<date>` →
`sync/<date>` compare filtered to the `docs/ohos-sync` path. Then:

```sh
git push --force-with-lease=ohos-main:pre-sync/<date> ohos ohos-sync-<date>:ohos-main
git push ohos pre-sync/<date> base/<date>
git tag sync/<date> ohos-sync-<date> && git push ohos sync/<date>
```

## After a sync: updating your branches

`ohos-main` is force-pushed by the sync, so local branches need a rebase —
the same routine one as after any upstream move:

- Set `git config pull.rebase true` once. After a sync, `git pull --rebase`
  on `ohos-main` and `git rebase ohos-main` on feature branches replay only
  your own commits: fork-point detection (your reflog of the remote branch
  knows the old published tip) excludes the old stack copies, and patch-id
  matching drops anything content-identical to the new stack.
- That covers the common case, not every case. It can trip when your clone
  has no reflog of the old tip (fresh clone, long-unfetched machine), or
  when you built directly on a patch the sync reshaped (conflict-resolved,
  shrunk, folded, superseded).
- The deterministic form needs neither reflog nor patch-id and is always
  correct about which commits are yours:

  ```sh
  git rebase --onto sync/<date> pre-sync/<date> my-branch
  ```

  Only genuine content conflicts between your work and the new base remain
  — those exist under any sync model.

## Device-test gotchas

- `ohos-test-runner` selects the device via `OHOS_TEST_RUNNER_HDC_TARGET`,
  not `HDC_TARGET`, and is not safe under nextest's concurrent list/run
  invocations (fixed device paths); wrap it in `flock` or run with a
  serialising wrapper.
- The repo's `.config/nextest.toml` slow-timeout (5 s × 4) kills device
  tests; pass `--config-file` with a profile whose period is minutes.
- `./mach package --ohos` cannot sign in a container whose signing config
  has short passwords (hvigor `00303116`); sign the unsigned HAP with
  `hap-sign-tool.jar` as `ports/arkweb/tools/build_test_app.py` does.

## Stack hygiene

- Folding conventions live in step 2 of the procedure; between syncs, land
  fixups as ordinary commits on `ohos-main` and let the next sync's fold
  step fold them.
- Keep the docs/policy/CI commits first on the stack so they rebase first.
- A patch that conflicts on consecutive syncs is a refactor-to-additive
  work item; note it in the manifest log.
